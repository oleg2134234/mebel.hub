# mebel.hub — правила проекта

Одностраничный статический каталог мебели для менеджеров по продажам.
Живёт по адресу **https://oleg2134234.github.io/mebel.hub/** (GitHub Pages, ветка `main`, корень репозитория).

## Обязательные правила

Нарушать нельзя, проверять на каждое изменение:

1. **Главное правило — один и тот же узнаваемый диван на всех слайдах карточки.** Модель нельзя перерисовывать, улучшать или подменять даже ради красивого кадра, белого фона или правильных выносок. Подробная проверка идентичности — ниже.
2. **Порядок слайдов в галерее** — фиксированный, менять местами запрещено. Полный список ниже, в разделе «Порядок слайдов в галерее».
3. **Большие видео — вне репозитория.** В git не коммитим видеофайлы тяжелее ~5 МБ и вообще ничего из папок `reels/`, `social/`, `story/`, `video/`. Подробности ниже, в разделе «Медиа и большие файлы».
4. **Габариты товара — длина и ширина обязательны** в `dims`, иначе товар выпадает из подбора. Подробности ниже, в разделе «Данные каталога».

### Визуальная идентичность модели — правило № 1

На каждом слайде одной карточки должен быть **тот же самый диван**, однозначно узнаваемый как одна модель. Допустимы только другой ракурс и штатные состояния этой же модели: сложенный, разложенный, открытый короб, крупный план.

Не должны меняться: силуэт и конструкция; число и форма модулей; пропорции; ширина подлокотников; форма спинки, сиденья и подушек; количество подушек; швы, стёжка и кант; ножки; полки и декор; ткань, её фактура и цвет. Нельзя добавлять или удалять детали, менять конфигурацию, превращать прямой диван в угловой/П-образный либо использовать похожую модель.

**При конфликте требований идентичность дивана важнее всего:** важнее белого фона, композиции, качества изображения, расположения линий и других правил. Если исправление меняет диван или точное совпадение нельзя подтвердить сравнением с остальными слайдами, результат не подключаем. Сначала ищем реальный кадр этой модели или редактируем только фон/графику детерминированно, не трогая пиксели предмета.

Перед подключением нового изображения сравниваем его минимум с главным реальным фото и другими ракурсами карточки: отдельно проверяем перечисленные выше признаки. Генеративный результат не принимаем по общему впечатлению «похож» — совпадение должно подтверждаться по деталям.

**После каждого готового исправления обязательно показываем справа в браузере полную карточку товара**, открыв её галерею на исправленном слайде. Недостаточно открыть прямую ссылку на файл изображения: пользователь должен видеть результат в реальном интерфейсе карточки, с названием товара, номером слайда и подписью. Карточку показываем до публикации, чтобы результат можно было проверить.

**При повторной замене уже показанного изображения обязательно меняем имя файла/версию URL** (`slide_dims-v2.png` → `slide_dims-v3.png`) и обновляем ссылку в галерее. Простое перезаписывание файла под прежним URL запрещено: браузер может оставить старую картинку в кэше. После изменения перезагружаем страницу и заново открываем полную карточку на исправленном слайде.

**Единственное явно одобренное пользователем исключение на 04.09.2026 — `43 Марк ДК`:** разрешено использовать `assets/mark-dk/slide5_dims-v2.png`. Это точечное решение не становится образцом и не ослабляет правило идентичности для других карточек.

## Что это технически

- **Один файл — `index.html`** (~1600 строк): весь CSS и весь JS встроены прямо в него. Больше кода нигде нет.
- **Нет сборки, нет зависимостей, нет `node_modules`, нет тестов, нет линтера.** Открыл файл — отредактировал — сохранил.
- Всё остальное в репозитории — медиа: фото и видео товаров.
- Внешние ресурсы не подключаются (шрифты системные, скриптов с CDN нет). Так и оставляем — сайт должен работать офлайн из папки.

## Структура

```
index.html              единственный код
assets/<модель>/         фото и видео карточек товара (slide*.jpg, video_*.mp4, scheme_*.jpg, real*.jpg)
assets/brand/            логотип и иконки интерфейса (logo.jpg, icons/*)
reels/  social/  story/  video/   материалы для соцсетей (в самом сайте НЕ используются — см. «Медиа и большие файлы»)

sync.ps1 / sync.sh       синхронизация между компьютерами
```

## Данные каталога — внутри `index.html`

Три JS-объекта в `<script>` (примерно строки 727–729), каждый — JSON в одну строку:

| Объект | Что это | Ключ |
|---|---|---|
| `PRODUCTS` | массив товаров (сейчас 44 шт.) | `id` (число) |
| `IMAGES` | id → путь к главному фото карточки | `id` |
| `GALLERIES` | id → `{title, slides:[{src,name,desc,type?}]}` | `id` |

Поле товара: `{id, title, category, dims, desc, colorIdx, hero?}`.

- `category` — одно из: `sofa`, `armchair`, `bed`, `mattress`, `other` (человеческие названия в объекте `CATS`).
- `dims` — строка `"Длина×Ширина×Высота"` в миллиметрах, например `"2360×1080×900"`. Диапазоны пишутся через тире: `"2000×800–1800×230–240"`.
- `colorIdx` — индекс в демо-палитре подбора по цвету.
- `hero: true` — карточка крупнее в каталоге.

### Габариты — длина и ширина обязательны (правило 3 из обязательных)

**У каждого товара в `dims` должны быть и длина, и ширина.** Подбор («квиз») фильтрует по длине и ширине; товар без любого из этих чисел просто не появится в результатах. Длина = большее из двух напольных измерений, всегда ≥ ширины. Высота в подборе не участвует. У матрасов ширина берётся из диапазона (`parseRange(dims, 1)`).

Формат дивана (прямой / угловой / П-образный) определяется не отдельным полем, а по тексту `title`/`desc`: `ДКУ`, `оттоман`, `угловой` → угловой; `п-образ` или суффикс `ДКУ-П` → П-образный (см. `matchesFormat`).

### Порядок слайдов в галерее (правило 1 из обязательных)

Слайды в `GALLERIES[id].slides` идут строго в этом порядке. Пропускать позицию можно (не у всех моделей есть все слайды), **менять местами — нет**.

1. **В интерьере** — визуализация модели в интерьере. Всегда первый.
2. **Уют** (или «Уютный вечер») — жанровая сцена с моделью в быту.
3. **Размеры** — слайд с габаритами в сложенном виде.
4. **Разрез** — разрез / рентген конструкции. Если есть.
5. **Видео: раскладка «…»** — схематичное видео механизма (если раскладка есть). Идёт сразу после «Размеры»/«Разрез». Реальные видео («облёт», реальная съёмка) — тоже здесь.
6. **Реальные фото товара** — по кругу вокруг предмета: «Общий вид» → «Вид спереди» → «Ракурс 3/4» → «Вид сбоку» → «Вид сзади».
7. **Разложенное состояние** — «В разложенном виде» → «Раскладка» → «Спальное место».
8. **Хранение** — «Бельевой ящик» / «Бельевой короб» (если справа и слева — сначала справа).
9. **Преимущества и особенности** — индивидуальные достоинства модели, после хранения и перед «Практичностью». Обязателен для каждой карточки, проходящей доработку.
10. **Практичность** — закрывающий слайд. Всегда последний, если присутствует.

Коротко: сначала блок «визуализации» (интерьер → уют → размеры → разрез → видео механизма) в фиксированном порядке, затем реальные фото (обход вокруг модели), затем раскладка и спальное место, затем хранение, «Преимущества и особенности» и «Практичность» в самом конце.

Первый слайд карточки в каталоге (`IMAGES[id]`) — это, как правило, «Общий вид» или «В интерьере»; он не обязан совпадать с первым слайдом галереи, но должен быть реальным фото или интерьерной визуализацией, не «Размерами» и не «Разрезом».

### Как делать слайд «Размеры» (обязательный процесс)

Слайд размеров **не рисуем с нуля** — берём фото товара из его галереи, удаляем только окружение и добавляем выноски. Форму, цвет, фактуру, пропорции и ракурс дивана не меняем.

**Обязательные требования пользователя от 04.09.2026 — для всех карточек, включая «Сандра 2 ДК»:**

- **Все числа на слайде «Размеры» — в сантиметрах.** Миллиметры переводим делением на 10 без потери точности: `2460 → 246`, `1065 → 106,5`, `945 → 94,5`, `2140 → 214`, `1500 → 150`. Десятичный разделитель — запятая; не округляем до целых.
- В капсулах оставляем только цифры (и десятичную запятую); в подписи слайда явно пишем «Размеры в сантиметрах» либо используем `см` после значений. Поле `PRODUCTS[].dims` остаётся в миллиметрах — это внутренний формат подбора, его не переводим.
- **Фон обязательно сплошной белый (`#FFFFFF`), непрозрачный:** только диван и размерные выноски, без комнаты, пола, ковра, посторонних предметов, градиентов и декоративных подложек. Прозрачность, шахматная сетка и серый фон не допускаются. Это правило действует для обеих панелей и пространства между ними.
- **Предпочтительное положение линий размеров — в нижней части дивана, от угла до угла его проекции на пол, на небольшом расстоянии от дивана.** Проекция на пол — только геометрический ориентир; сам пол и дополнительные контуры проекции не рисуем, фон остаётся белым.
- **Линия сверху допускается**, когда так компоновка получается чище: она должна быть строго параллельна соответствующей грани дивана, находиться полностью снаружи предмета и нигде не заходить на диван. Её концы по-прежнему соответствуют двум углам измеряемой грани и имеют одинаковый небольшой перпендикулярный отступ. Нельзя ставить линию сверху только ради свободного места, если она перестаёт соответствовать измеряемой грани.
- **Допустимый частный случай для разложенного дивана:** линию глубины спального места можно расположить сверху, за спинкой, как выноску над верхним контуром. Она должна идти параллельно направлению глубины спального места, располагаться целиком на белом поле, не касаться спинки и подлокотников и не пересекать диван. Нижнюю линию длины при этом можно оставить под передним краем спального места. Такое разнесение двух размеров считается правильным и помогает не создавать пересечение линий в одном нижнем углу.
- **Каждая размерная линия строго параллельна соответствующей стороне проекции на пол в перспективе кадра.** Оба её конца отстоят от соответствующих углов проекции на одинаковое небольшое перпендикулярное расстояние. Не выравниваем все линии по горизонтали или вертикали независимо от ракурса и не уносим выноски далеко от дивана.
- Геометрия строится по двум углам проекции измеряемой стороны на пол `A` и `B`: концы выноски — `A + n*d` и `B + n*d`, где `n` — единичная нормаль к стороне проекции, `d` — один и тот же небольшой внешний отступ. Координаты углов проверяем по фото; линии и цифры предпочтительно наносим детерминированно, а не поручаем нейросети угадывать их положение.
- Линия находится снаружи дивана, не пересекает его; на концах одинаковые кружки, капсула с числом — по центру. Отступы выносок в пределах панели визуально согласованы. Размеры спального места относятся к поверхности для сна, не к наружным краям подлокотников.
- Перед подключением проверяем обе панели: фон белый, предмет не изменён, значения в сантиметрах; нижние линии привязаны к углам проекции на пол, верхние — к углам соответствующей грани; отступы небольшие и равные; линии параллельны измеряемым граням, полностью находятся снаружи предмета, не заходят на диван; цифры и выноски не обрезаны.

**Структура слайда — фиксированная.** Итоговый «Размеры» — это две панели, склеенные вертикально:

- **верхняя панель — диван в сложенном виде**, с габаритами (ширина × глубина; при виде сбоку добавляется высота);
- **нижняя панель — диван в разложенном виде**, с размерами спального места (длина × ширина).

Панели готовим **по отдельности**: сначала каждый кадр отдельно — с нанесёнными выносками и цифрами, — и только потом склеиваем оба в один слайд `assets/<модель>/slide_dims.jpg`. Порядок панелей менять нельзя: сложенный вид всегда сверху, разложенный всегда снизу. Если разложенного кадра у карточки нет — сначала добавить его обычным слайдом в галерею (см. п. 1), слайд «Размеры» без нижней панели не выпускаем.

1. **Исходники — те же кадры, что уже в галерее этой карточки:** берём фото сложенного вида (для верхней панели) и разложенного вида (для нижней) прямо из слайдов товара. Новые кадры не подбираем и диван заново не генерируем — слайд «Размеры» должен быть теми же фото, что видит покупатель в остальной галерее. Если в карточке нет разложенного вида — доснять/взять у производителя (mebvektor.ru) и сначала добавить его обычным слайдом в галерею.
2. **Подготовка и выноски.** Сначала удаляем окружение исходного фото, сохраняя сам диван без изменений. Затем наносим линии по геометрическому правилу выше (линия + кружки на концах + капсула). Сгенерированные выноски без проверки геометрии не принимаем. Старые скрипты и сервисные примеры ниже не отменяют эти требования. Ключ Kie.ai: `<домашняя папка>\.claude\kie_api_key.txt` (у каждой машины свой).
   - Эндпоинт: `POST https://api.kie.ai/api/v1/jobs/createTask`, `Authorization: Bearer <key>`.
   - Тело: `{"model":"nano-banana-pro","input":{"prompt":"…","image_input":["<URL реального фото>"],"aspect_ratio":"4:3","resolution":"2K","output_format":"png"}}`.
   - Опрос: `GET https://api.kie.ai/api/v1/jobs/recordInfo?taskId=…` до `data.state == "success"`, затем ссылка в `JSON.parse(data.resultJson).resultUrls[0]` (живёт ~24 ч — скачивать сразу).
   - Фото отдаём по URL с GitHub Pages: `https://oleg2134234.github.io/mebel.hub/assets/…`.
   - Рабочий скрипт-образец: `tools/gen-dims-slide.ps1` (на примере Адель 4 КК).
3. **Промпт для удаления фона** (EN, суть): «Remove only the surrounding room, floor and props; isolate the exact sofa on a solid opaque pure white background (#FFFFFF). Preserve the sofa pixel-for-pixel: color, fabric texture, proportions, silhouette, camera angle and all details. Do not redesign, redraw, duplicate or simplify the sofa. No text, no dimensions, no transparency, no checkerboard pattern, no gray background, no gradients». Для одной панели — ровно один предмет. После удаления фона сверяем с исходником. Оформление выносок: тонкая тёмно-графитовая линия, кружок на каждом конце, тёмная капсула с белым жирным числом в сантиметрах. Эталон графики — [tools/dims-style-ref.jpg](tools/dims-style-ref.jpg); новые требования к фону, единицам и геометрии имеют приоритет над старым эталоном.
4. **Числа** — из подтверждённых данных производителя, на слайде обязательно в сантиметрах. Для трансформера: сложенный вид — ширина/глубина (и высота при виде сбоку); разложенный — длина спального × ширина спального. Неподтверждённые значения не придумываем.
5. **Сборка слайда — своими силами** (не в нейросети): склеить панели вертикально, сложенный вид сверху, разложенный снизу, обязательно сплошной непрозрачный белый фон `#FFFFFF`, небольшой белый зазор. Уменьшить до ~1200 px по ширине, сохранить как `assets/<модель>/slide_dims.jpg`. При смене имени обновить ссылку в галерее. Исходник сохранять до проверки новой версии.

### Как делать видео облёта (360°)

Модель — **`kling/v2-5-turbo-image-to-video-pro`** на Kie.ai (дешевле и качественнее Wan/Seedance для этой задачи: ~42 кредита за 5-сек клип).

1. **Вход — ДВА реальных кадра** товара: `image_url` (стартовый — вид спереди 3/4) и `tail_image_url` (конечный — вид сзади). Оба — официальные фото производителя из `assets/<модель>/` (front + back), по URL с GitHub Pages.
2. **Тело запроса:** `{"model":"kling/v2-5-turbo-image-to-video-pro","input":{"prompt":"…","image_url":"<front>","tail_image_url":"<back>","duration":"5"}}`. Эндпоинт и опрос — как у слайдов размеров (`jobs/createTask` → `jobs/recordInfo` → `resultJson.resultUrls[0]`).
3. **Промпт (EN, суть):** плавный непрерывный облёт камеры на 180° по часовой, старт ровно на первом кадре, финиш ровно на последнем; предмет **неподвижен и не деформируется — сохранить цвет, фактуру, пропорции**; фон ровный светло-серый студийный, без людей и зума.
4. **Полный 360 — из двух клипов:** A (перед→зад) + B (зад→перед, кадры местами), склеить своими силами. Перед и зад берутся с реальных фото, «плавает» только на боковых четвертях. ~84 кредита на диван.
5. Готовый mp4 класть в `assets/<модель>/video_orbit.mp4`, слайд в галерее — тип `video`, имя «Видео: облёт», в блоке видео (после «Видео: раскладка»).

## Оформление

- Тема светлая/тёмная — **только через CSS**: `@media (prefers-color-scheme: dark)` + переопределения `:root[data-theme="..."]`. Следует за настройкой ОС, ручного переключателя нет.
- Цвета — через CSS-переменные в `:root` (`--bg`, `--surface`, `--ink`, `--accent`, `--gold`, ...). Хардкод цветов в правилах не добавляем — только переменные.
- Весь текст интерфейса — русский. Кавычки — «ёлочки», тире — длинное (—).

### Шрифт

- **Один шрифт на весь проект — Inter**, самохостинг в `assets/fonts/` (2 файла woff2, variable-начертание: `inter-latin-wght-normal.woff2` + `inter-cyrillic-wght-normal.woff2`). Внешних CDN нет, работает офлайн. Заголовки и текст — один и тот же Inter (никаких serif).
- Базовый кегль — на `html`: `font-size: clamp(1rem, 0.95rem + 0.3vw, 1.15rem)`. Отталкивается от системного размера шрифта устройства, чуть подрастает на широких экранах, ограничен сверху. **Весь макет свёрстан в `rem`** — размер меняется этим одним правилом, поштучные `font-size` не трогаем.

### Адаптивность

Дизайн резиновый, но **структура и восприятие едины на всех экранах** — на широком мониторе не должно превращаться в другой макет.

- Каталог `.grid`: `repeat(auto-fill, minmax(240px, 1fr))`, `max-width: 1240px` — столбцы добавляются сами по ширине экрана, карточка везде одинаковая. Шапка каталога сжимается при прокрутке (класс `.compact` на `header.site`).
- Модалки (`.quiz-modal`, галерея): `max-height` в `vh` + внутренняя прокрутка. Должны помещаться в экран без вылезания.
- Единицы — `rem` / `%` / `clamp()` / `vw`. Фиксированные `px` только для мелочей (толщина рамок, радиусы).

### Иконки в рамке-плитке

Правило для всех кнопок вида «иконка + подпись в квадратной плитке» (типы мебели в квизе, условия ткани, плитки на главной):

- **Иконка занимает ~3/4 плитки.** Белое/светлое поле плитки — тонкая рамка вокруг иконки, не наоборот.
- Размер иконки задаётся **в процентах от плитки** (`width: ~74–80%`), чтобы иконка росла вместе с плиткой на широких экранах.
- Плитка квадратная (`aspect-ratio: 1 / 1`), маленькое внутреннее поле (`padding: ~4–5%`).

## Медиа и большие файлы

**Правило 2 из обязательных.** Репозиторий и так раздут (~500 МБ истории), поэтому:

- **Ничего тяжелее ~5 МБ в git не коммитим.** Особенно видео.
- **Папки `reels/`, `social/`, `story/`, `video/` — не для git.** Это исходники для соцсетей, сайт их не открывает. Хранить во внешнем месте (облачный диск, отдельное хранилище). В идеале этих папок в репозитории быть не должно — вместо них `README` со ссылкой на хранилище. Новые SMM-ролики сюда не добавляем.
- **Видео, которые нужны сайту** — только `assets/<модель>/video_*.mp4` (схемы раскладки, короткие облёты). Цель — **≤ 3 МБ**, потолок **5 МБ** на файл. Больше — пережать перед коммитом: H.264, до 720p, пониженный битрейт, без звука если он не нужен.
- **Фото** — JPG, разумное разрешение (ширина ~1600 px достаточно для слайда), с компрессией. PNG только для иконок с прозрачностью.
- Если по-настоящему большой файл всё же обязан быть в репозитории — только через **Git LFS**, не обычным коммитом.

Проверка перед `sync.ps1 end`: `git diff --cached --stat` — если видишь мегабайты, останови коммит и разберись.

## Синхронизация между компьютерами

Проект ведётся с двух компьютеров **по очереди** (например: утром — компьютер A, вечером — компьютер B). Одновременно на обоих не работаем.

**Единственный источник правды — GitHub.** Между машинами передаём только через `git push` / `git pull`.

### Чего нельзя делать

- ❌ Копировать папку проекта вручную (флешка, «перекину архив»).
- ❌ Держать папку в OneDrive / Dropbox / Google Drive / Яндекс.Диске — они повреждают `.git` при частичной синхронизации.
- ❌ Работать, не сделав `sync start` в начале.
- ❌ Заканчивать день, не сделав `sync end`.
- ❌ Держать проект в `Downloads` (некоторые чистилки его подчищают) — перенеси в стабильную папку, например `C:\dev\mebel.hub`.

### Разовая настройка на каждой машине

Один раз на компьютере, где проекта ещё нет:

```bash
git clone --depth 1 --single-branch --branch main https://github.com/oleg2134234/mebel.hub.git
cd mebel.hub
git config pull.rebase true
```

`--depth 1` — поверхностный клон без истории (история ~500 МБ, полный клон качается очень долго). Для правки `index.html` и ассетов история не нужна.

Если позже `git pull` заругается на `shallow` — один раз выполнить `git fetch --unshallow` (это разово докачает историю).

### Ежедневный ритуал (обе машины одинаково)

**1. Начинаешь работу — подтяни изменения с другой машины:**
```powershell
.\sync.ps1 start
```
Git Bash: `./sync.sh start`

Делает `git pull --rebase --autostash`. После «Готово. Репозиторий актуален» — можно править файлы.

**2. Закончил работу — сохрани и отправь:**
```powershell
.\sync.ps1 end "что сделал за сессию"
```
Git Bash: `./sync.sh end "что сделал за сессию"`

Делает: zip-бэкап в `backups/` → `add -A` → `commit` → ещё раз `pull --rebase` → `push`. После «Отправлено» — можно выключать компьютер.

Правило простыми словами: **сел работать → `start`. Встал из-за компьютера → `end`.** Каждый раз, на любой из машин.

### Передача работы с машины 1 на машину 2

Чтобы вечером на машине 2 сразу продолжить с того же места:

1. **Машина 1, конец работы:** `.\sync.ps1 end "…"` и дождись строки **«Отправлено»**. Пока её нет — работа не ушла на GitHub, машина 2 её не увидит. Не закрывай терминал до этой строки.
2. **Машина 2, начало работы:** `.\sync.ps1 start`. Через пару секунд там ровно то состояние, на котором закончила машина 1 — можно править дальше.

Между этими двумя шагами ничего вручную переносить не нужно. Единственное условие — на шаге 1 был интернет и `push` прошёл. Если интернета не было, машина 1 остаётся «ведущей»: садиться за машину 2 нельзя, пока не сделаешь `push` с машины 1.

Мини-чеклист смены: `end` → «Отправлено» → пересел → `start` → «Актуален» → работаешь.

### Типичные ситуации

| Ситуация | Что делать |
|---|---|
| Забыл `start`, уже что-то наменял | Просто запусти `.\sync.ps1 end "…"` — внутри он сам подтянет чужое через `--rebase` и наложит твоё поверх. |
| `start` пишет про конфликт | Открой файл из сообщения, найди `<<<<<<<` / `=======` / `>>>>>>>`, оставь нужный вариант, `git add <файл>`, затем `git rebase --continue`. Конфликты возможны только если обе машины правили один и тот же кусок `index.html`. |
| `end` пишет `push` отклонён | Значит на другой машине был свежий `end`. Запусти `.\sync.ps1 end "…"` ещё раз — он сделает `pull --rebase` и повторит `push`. |
| Совсем запутался в состоянии git | `git status`, потом спроси Claude Code — не делай `reset --hard` наугад, потеряешь работу. |
| Работал на машине без интернета | Коммить локально (`git commit`), `push` сделаешь, когда появится сеть. На другую машину не пересаживайся, пока не запушил. |

### Как быстро воспроизвести аудит

Контактный лист по карточке (все слайды одной модели в одной картинке) собирается
скриптом на PowerShell + System.Drawing — Node/Python на машине нет. Логика:
прочитать `PRODUCTS`/`GALLERIES` из `index.html` в JSON, для каждой карточки
категории `sofa` сложить миниатюры слайдов сеткой 4 в ряд с подписями
`[индекс] имя` и именем файла. Порядок слайдов отдельно проверяется скриптом
по рангам из раздела «Порядок слайдов в галерее».


## Доработка каталога с 05.09.2026

План: [docs/catalog/PLAN.md](docs/catalog/PLAN.md). Журнал: [docs/catalog/CHANGELOG.md](docs/catalog/CHANGELOG.md). За один шаг дорабатываем один ID, показываем полную карточку и фиксируем результат. Данные аудита — снимок, а не утверждение о состоянии после исправлений.

### Крупный товар в кадре

- Товар — главный объект. На общем виде занимает ориентировочно 75–90% полезной ширины кадра, показан целиком; подлокотники, ножки и оттоманка не обрезаны.
- Убираем лишнее окружение кадрированием только при сохранении предмета. Не растягиваем и не перерисовываем мебель. Малое разрешение не исправляем выдуманными деталями.
- В галерее используем contain, сохраняем пропорции; проверяем крупный экран и узкую панель/телефон. Текст и декор не закрывают мебель.

### Новый слайд «Преимущества и особенности»

- Точное название: «Преимущества и особенности». После хранения, перед финальной «Практичностью»; если её нет — последний.
- Крупное неизменённое фото именно этой модели и 2–4 коротких индивидуальных факта. Каждый факт объясняет пользу: особая оттоманка, подушки, хранение, конструкция, подтверждённые опции.
- Только видимые на фото или подтверждённые источником свойства. Не выдумывать нагрузку, медицинские свойства, гарантию, «антикоготь», состав и комплектацию.
- Допускается адаптивный HTML/CSS-слайд type: features с исходным фото в src и features: [{title,text}]. Это сохраняет реальную мебель и читаемый текст без повторной генерации изображения.
- Числа и комплектация должны соответствовать конкретному ID. Источник и дата — в журнале, покупательские подписи без служебных комментариев.
- Новый тип проверяется tools/audit-catalog.js. Счётчик обозначает слайды, а не выдаёт текстовый слайд за дополнительное фото.
